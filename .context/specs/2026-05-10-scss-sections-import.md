# Спецификация: импорт SCSS/CSS-переменных с группировкой по секциям

## Контекст

Сейчас CSS/SCSS-парсер (`crates/parser/src/css.rs`) складывает все найденные
`$var: …` / `--var: …` объявления в одну палитру «Variables». Пользователь хочет
импортировать большие dump-файлы дизайн-токенов вида:

```scss
// Gray Scale
$gray-50: #fafafa;
$gray-100: #f5f5f5;
...

// Primary Colors (Ocean Theme)
$ocean-50: #f0fdfa;
$ocean-400: #40e0d0; // Main turquoise
...

// Status Colors
$success-50: #f0fdf4;
$error-50: #fef2f2;
$warning-50: #fefce8;
...
```

и получить осмысленный набор палитр («Gray Scale», «Primary Colors (Ocean
Theme)», «Status Colors», …) вместо одной свалки.

## Требования

### Функциональные

1. Парсер CSS/SCSS определяет **секции** по комментариям-заголовкам, стоящим на
   отдельной строке: `// текст` (SCSS) или однострочный `/* текст */` (CSS).
2. Все переменные от заголовка секции до следующего заголовка (или конца ввода)
   образуют **одну палитру** с именем = текст заголовка. Внутри секции переменные
   **не дробятся** дополнительно.
3. Переменные, объявленные **до первого заголовка секции** (а также весь ввод,
   если заголовков секций нет вовсе), группируются **по общему префиксу имени**:
   - префикс = часть имени переменной до последнего `-` (`deep-blue-800` →
     `deep-blue`, `gray-50` → `gray`, `white` → префикса нет);
   - группа из **≥ 2** переменных с одинаковым непустым префиксом → отдельная
     палитра с именем = префикс;
   - все остальные переменные (одиночки, переменные без префикса) → одна палитра
     «Variables», в порядке появления.
4. Имя цвета внутри палитры — **полное имя переменной** (`gray-50`, `ocean-400`,
   `white`). Если в значении одной переменной несколько цветов — первый получает
   имя переменной, остальные `name-1`, `name-2`, … (как сейчас).
5. **Трейлинг-комментарии** после кода (`$ocean-400: #40e0d0; // Main turquoise`)
   игнорируются — на имя цвета не влияют (как сейчас).
6. Поведение **автоматическое**: новых опций/тоглов в UI и в `ParseOptions` нет.
   Если группировать нечего (нет секций, нет общих префиксов) — результат как
   раньше: одна палитра «Variables».
7. Пустые секции (заголовок без последующих переменных) не создают палитру.

### Нефункциональные

- Изменения локализованы в `crates/parser` (Rust). Фронтенд, IPC-DTO,
  `lib.rs`-флоу не трогаем.
- `css.rs` не превышает 200 строк (правило проекта) — при необходимости вынести
  группировку по префиксу в отдельный модуль `css_group.rs`.
- Существующие unit- и snapshot-тесты парсера остаются зелёными без изменений
  снапшотов (плоские списки переменных без `-` и без секций → «Variables»).

## Архитектура

`css::try_parse(input)` переписывается с построчного сканирования:

1. Классификация строк:
   - **section header**: строка целиком — комментарий: `^\s*//\s*(.*)$` или
     `^\s*/\*\s*(.*?)\s*\*/\s*$`. Пустой текст после очистки → строка-комментарий,
     но «pending-заголовок» не обновляет.
   - **var decl**: текущий regex `(?:--|\$)([A-Za-z0-9_-]+)\s*:\s*([^;\n]+)`,
     значение должно содержать хотя бы один цвет (`extract_colors`).
   - **прочее** (`:root {`, `}`, пустые строки, строки с кодом и трейлинг-
     комментарием) — игнорируется, на pending-заголовок не влияет.
2. Накопление в `Vec<Section>` где `Section { name: Option<String>, vars: Vec<(String, ColorValue)> }`:
   - `pending: Option<String>` обновляется на каждой непустой строке-комментарии
     (последняя непустая строка из подряд идущих комментариев побеждает);
   - на var-decl: если `pending.is_some()` → начать новую `Section` с этим именем
     и `pending = None`; иначе — добавить в последнюю `Section`; если секций ещё
     нет — создать стартовую `Section { name: None, … }`.
3. Сборка `Vec<ParsedPalette>` в порядке секций:
   - `name: Some(n)` → одна палитра `n` со всеми цветами секции;
   - `name: None` → группировка по префиксу (см. требование 3), может дать
     несколько палитр + хвостовую «Variables».
4. Пустой результат → `None` (как сейчас, чтобы сработал табличный/fallback-путь).

## Edge Cases

- Ввод вообще без переменных → `try_parse` → `None`.
- Заголовок секции без переменных → секция отбрасывается.
- Несколько подряд строк-комментариев перед секцией → имя = последняя непустая.
- Пустой комментарий `//` между заголовком и переменными → не сбрасывает секцию.
- Пустая строка между заголовком и переменными → не сбрасывает секцию.
- Переменные до первого заголовка + дальше секции → «до-секционные» идут через
  префикс-группировку и стоят первыми в результате.
- `$white`, `$black` (без префикса) в секции → попадают в палитру секции как
  обычные цвета с именами `white`, `black`.
- `$white`, `$black` вне секций → в «Variables».
- `--var` в CSS без `/* */`-заголовков → как раньше: префикс-группировка или
  «Variables».
- Значение с несколькими цветами (`$grad: #fff #000`) → `grad`, `grad-1`.

## Риски и митигации

- **Регрессия снапшотов.** Митигация: существующие фикстуры без `-` и без секций
  → «Variables», поведение не меняется; прогнать `cargo test --workspace`.
- **`css.rs` > 200 строк.** Митигация: вынести `group_by_prefix` в `css_group.rs`.
- **Ложное определение секции** (строка `// …` внутри значения многострочного
  правила). Маловероятно для палитр-dump'ов; принимаем.

## Тестовая стратегия

Unit-тесты в `css.rs` (рядом с модулем):
- секции по `//` → отдельные палитры с правильными именами и цветами;
- однострочный `/* Section */` → секция;
- несколько подряд комментариев → имя = последняя непустая;
- переменные до первой секции → префикс-группировка;
- нет секций, есть префиксы (`$gray-50..200`) → палитра «gray»;
- правило ≥ 2: `$gray-50`, `$gray-100`, `$white` → «gray» (2 цвета) + «Variables» (white);
- трейлинг-комментарий игнорируется → имя цвета `ocean-400`;
- существующие тесты `parses_css_custom_properties`, `parses_scss_variables`,
  `no_match_returns_none` остаются зелёными.

Snapshot-тест в `crates/parser/tests/snapshots.rs`:
- `snapshot_scss_sections` — репрезентативный кусок ввода пользователя (Gray Scale
  + Ocean + Status Colors с success/error/warning + `$white`/`$black` секции
  Semantic Colors), новый `.snap`-файл.

Проверки (`.context/checks.md`): `cargo fmt --all -- --check`,
`cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`,
`pnpm check`.
